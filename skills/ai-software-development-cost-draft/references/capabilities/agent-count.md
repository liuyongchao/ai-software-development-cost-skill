# 独立智能体与内部节点判定

## R — 原文

> 同时满足以下条件，可判定为1个独立的人工智能智能体：具备独立业务入口、独立交互界面或独立API；拥有独立知识库、提示词、编排逻辑与业务规则；可独立部署、独立启停、独立交付、独立完成业务目标。

出处：6.3.3.2 a)6)，PDF第20页；同类任务包与复用见a)4)，PDF第19页。

## I — 自述

先画清一项业务从输入到完成的闭环，再检查其中哪些对象真的独立。  
第一组入口形式是“或”：独立业务入口、界面或API满足一种即可。  
第一组成立仍不够，知识库、提示词、编排逻辑与业务规则也要独立。  
还须能够独立部署、启停、交付并完成自己的业务目标。  
同一闭环中的角色、子任务、分支和节点，只登记为内部复杂度。  
缺失第二或第三组证据时，输出待确认，不把一个API直接换算为一个智能体。  
确认多个独立对象后可分别评估工作包，并对共享成果保留复用关系。

## A1 — 应用示例

原书未提供独立智能体计数的完整案例。以下为合成演练：客服与报修各有独立API、知识库、提示词、编排逻辑、业务规则，均能独立部署启停交付并完成各自目标；客服内部含3个角色和5个分支节点。逐组核验后确认2个智能体，客服角色与节点不增加数量，留作复杂度输入。

变体：某组件只证明有独立API，其知识与业务逻辑、独立交付能力未知。结论为第一组满足，另两组待补，独立数量待确认；不是直接计1或永久计0。两种演练均没有真实项目实施结果。

## A2 — 未来触发

- 报价把每个角色都列成智能体：“一个客服流程有十个agent吗？”／agent count, multi-agent roles。
- 方案有多个独立API：“每个接口算一个吗？”／independent API, agent independence。
- 编排图分支和工具节点很多：“节点多是否多算智能体？”／workflow nodes, branches。
- 多业务共用知识库或统一部署：“这些能分别交付吗？”／shared knowledge base, independent delivery。

与“独立传统模型数量判定”的区别：本卡以智能体的三组独立性和业务闭环为判据，不用传统模型的单独采集标注训练规则代替。复杂度登记也不等于已经选定复杂度系数。

## E — 执行

输入契约：每个候选提供ID、业务目标及闭环范围、入口/界面/API证据、知识库和提示词、编排逻辑与业务规则、独立部署/启停/交付/目标完成证据，以及所属父流程、角色、分支、工具调用和共享成果关系。证据可为需求、配置、部署或验收记录引用；各检查项用已证实、已否定、未知状态。数量单位“个”，内部角色与节点另列。

1. 建立对象及父子关系表，写明每个业务闭环的起止与成果。完成标准：候选属于独立业务对象还是内部组件有证据；边界不明者已列问题。
2. 核第一组：独立入口、交互界面、API至少一个成立；再分别核第二组的知识库、提示词、编排逻辑、业务规则，以及第三组的部署、启停、交付、完成目标能力。三组共同满足才确认独立。完成标准：逐项留证，不能用一个“独立”总标签掩盖缺项。
3. 同闭环内部子任务、多角色、条件分支、编排节点归回父对象，独立增量计数为0，复杂度事实继续保留。共享导致边界无法判定或任一组未知时，暂停该对象数量结论。完成标准：已证实内部节点与证据不足对象分列，后者不被强判0或1。
4. 输出“候选—三组逐项状态—证据—父流程—判定—计数归属—复杂度记录—缺项”表，汇总已确认数量，明确是否仍有未决对象。对多个独立对象关联各自工作包、复用成果和数据活动；数据按实际活动排重。完成标准：确认数可追溯，内部复杂度未重复进入数量。

如需结构化登记，先读 `calculator-guide.md`，再按说明使用 `project-template.json`；`cost_calculator.py`不会验证接口或交付材料的真实性。

## B — 边界

一个独立API只满足第一组，不能推定另两组；首组也不要求三种入口同时具备。共享知识库、多场景共用入口等未覆盖边界保留待确认，不擅造豁免。单智能体不等于没有编排工作；内部复杂度不加数量，也不意味着工时为零。附录参数仅供参考，不能由节点事实自动映射档位。

## 相关能力

对比“独立传统模型数量判定”：两者都负责计量排重，但证据门槛不同；先识别模型或智能体，再各自执行。
